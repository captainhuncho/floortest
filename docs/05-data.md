# 05 · Data: where it lives and who can see it

Table-by-table detail, query rules, migrations and backups: `docs/DATABASE.md`. This file answers **where** and **who**. Add a table, a column holding personal data, or a permission → update this file in the same commit.

## Where data lives

| Data | Store | Region | Kept |
|---|---|---|---|
| Accounts, tracks' details, decisions, messages, logs | Postgres (Neon) | London | until deleted (see retention) |
| Audio, stems, covers, collection art, track artwork | Cloudflare R2, private bucket | EU/US edge | with its track/account |
| Verification proof (screenshots, PDFs staff upload when verifying an account; owner, 1 Nov) | Cloudflare R2, private bucket, `verification/<random>` keys | EU/US edge | while the account exists |
| Outgoing email copies (sign-in codes and private links stored hidden; the real text of an email still waiting to send is kept sealed with a key from `APP_SECRET` and erased once it has gone or given up; `delivery` is Resend's report: delivered, delayed, soft bounce, bounced or marked as spam, where a bounce after delivery is kept as a note in `delivery_detail` and never replaces Delivered, and only a hard bounce on an email that never arrived, or a spam report, stops email to the address; `delivered_at` and `delivery_detail`, migration 0136) | `outbox` table + Resend | Resend (US) | per Resend retention |
| Error reports | Sentry (browser reports only after Accept on the cookie banner; server reports always, without IP or personal data) | US | 90 days |
| Visit stats | Vercel Analytics (no cookies; only after Accept on the cookie banner) | US | per Vercel |

Files are never public: the app hands out short-lived signed links after checking who's asking.

## Who can see what

| Who | Can see |
|---|---|
| Receiver | their own account, collections, tracks sent to them, senders' names/emails/links, their own logs |
| Team member (held) | the account's desk while they're on it (tracks, senders, notes, replies, activity), with the plan's features; Members may edit collections and artwork (owner decision F5); never the owner's security, billing or plan settings; nothing of the team after they leave or are removed |
| Sender | their own receipts (by private token or confirmed email), not the receiver's notes. Every lookup of a receipt token and every receipt link goes through `src/lib/receipt-token.ts` (2 Nov), so how the token is stored changes in one place; a test fails if code bypasses it. The token is found by `tracks.token_hash` and rebuilt from `tracks.token_sealed` (migration `0126`; old rows get them on first read and nightly). The plain `token` was cleared by migration `0127` (plan B11) and is no longer written or read |
| Anyone holding a receipt link only | what happened and when, and the sender's email masked; the track, receiver, callout and note after proof (the browser it was sent from, the sending account, or an emailed code; owner 2 Nov). Read-only from day 90 (or once played out) and closed 90 days later (see Retention); a closed link shows only "This receipt has closed" |
| Anyone holding a private link (receipt, sender history, team invite, email confirmation) | that page, with the email it was sent to masked (`m•••@g•••.com`, owner 2 Nov); the full address only when signed in as its account. Pages not stored by browsers or caches (`Cache-Control: private, no-store`) |
| Share-link recipient (held) | only that collection's tracks sent while it allowed sharing, after an email code (or confirmed-email sign-in) and the access notice; listen, download only if granted; account holders also by `/c/a.<id>` while signed in (that visit ends at sign-out); never other collections, senders' details or the owner's notes |
| Ops, by permission | **Customer Care**: overview, inbox, feedback, emails, user support (suspend/restore/notes), verification, partners. **Developer**: incidents, jobs, storage, speed, security, switches (per-feature rollouts; site-wide switches such as Beta started are read-only, the super admin's), metrics. **Product Lead**: metrics, feature use, feedback, announcements, site content, switches (the same), plans (view), partners. **Sales & Marketing**: plan requests, waitlist, invites, partners, revenue, announcements, emails (view), metrics |
| Verification proof and history | everyone with **Verification** (Users (view) alone sees only the state and the date; the reason is never stored on the account, so the artist's own settings can't carry it) (the account page's history fold, Verification → Proposals waiting); proof files only through `/api/admin/verification-proofs/[id]`, which answers 404 alike for no permission and a missing file (images open in the browser, PDFs download). **Verification** proposes; **Verification (add the mark directly)** and **Verification (approve or decline proposals)** are never role defaults: the super admin ticks them per person on Ops team; nobody approves their own proposal |
| Super admin only | ops team, takedowns, data requests/exports, admin log, editing plans/prices or someone's plan, deleting/erasing accounts, changing email/handle, resetting two-step, signing someone out everywhere, View as, users CSV |

Every ops page and action names its permission (`src/lib/ops-perms.ts`); the build fails if one doesn't.

In the database, work done as a signed-in person (role `ft_person`) reads only the `users` columns the app shows about a person and changes only that person's own profile fields (migration 0108): never a teammate's password hash, two-step secret, recovery codes or Google id. A team desk FloorTest has suspended is shut to its teammates there too (migration 0109). `npm run check:perms` fails if `ft_person` can touch a secret column. Recovery codes are stored as HMACs keyed with `APP_SECRET` (older plain hashes work once each), and the Security page's device ids are keyed with it too, never the session's token hash.

Receipt proof cookie (owner, 2 Nov): `ft_receipt`, set when a send completes in a browser and after a receipt code. Signed with `APP_SECRET`, HttpOnly, Secure on the live site, SameSite=Lax, 30 days; it lists up to 20 sender ids, each with a keyed hash of that sender's email at the time (never the address), so it opens only that sender's receipts and stops working if the email changes or the sender is erased (`src/lib/receipt-proof-core.ts`). Strictly necessary, like `ft_sender`; the cookie policy should list it (owner/legal).

Browser sessions (`web` rows in `sessions`) remember the device that signed in (a label like "Chrome on macOS", never the IP) and when they were last used (written at most hourly); one nobody has used for 14 days ends, and the Security page lists them with a Sign out for each. The mobile app signs in as an `app` row in `sessions` (refresh token stored hashed; `created_at` keeps the first sign-in through every refresh, and the sign-in ends 90 days after it); it holds no database or storage keys, and "sign out everywhere", password changes and suspensions end it like any browser session. A password change or reset also ends the person's ops sessions (`admin_sessions`, 30 minutes idle at most) and marks their unused `password_resets` rows used. Browser cookies only ever match `web` sessions. Files shared into the app wait in the app's own app-group folder on the phone until sent or removed (cleared after a day); nothing is uploaded until the sender presses Send. **Offline kept tracks** (opt-in, Prepare → Save for offline): copies of the receiver's kept tracks in the app's private storage, excluded from phone backups. The copy always matches the last sync (cleared or deleted tracks, including auto-deleted ones, leave at the next sync), is wiped on sign-out, on reaching sign-in, when another account syncs, and after 30 days without opening Prepare online. Download links are signed per track and receiver and last an hour; saving offline isn't recorded as a "Download" on the sender's receipt. A phone signed out from another device keeps its offline copies until the app next reaches sign-in online, up to those 30 days. App data is left out of Android cloud backup and phone-to-phone transfer, and signing out empties the share inbox.

Ops reaching into the main site (on-page editing, read-only "View as") is bound to the exact ops session that started it: signing out of ops or its timeout ends it at once.

## Retention and deletion
- Receipt links (owner, 4 Nov, "go 90", then "same clock for all, plus the stems hold"): close 90 days after the track's final outcome (`src/lib/receipt-life.ts`). The outcome is the same for every track, whatever the receiver decided: played out (the sender sees it) or upload + 90 days, whichever comes first. So every receipt turns read-only by day 90 and closes by day 180, and the receipt never reads the decision or the file's removal. While stems are asked for and none has been sent, the receipt stays open for them (the sender sees the request); once one lands the normal clock applies. Read-only: no new stem upload, no stop sharing and no artwork (refused by the server); a stem started while it was open still finishes after the close, from the sender or the held batch. "Already has artwork" is kept through a delete by `tracks.art_attached_at` (migration `0128_track_art_attached`), and a deleted track's late stems and artwork are queued for removal, so neither tells the sender of the delete; a closed link shows only "This receipt has closed" (a 200 page, where an unknown link gets 404), and every other receipt route answers as an unknown link's, except that a stem started while it was open still completes. A receiver's stems request on a track no stem was ever sent for reopens a read-only or closed receipt until one arrives (the sender is emailed the request anyway). Nothing is deleted by this: the sender's history (`/sent`, confirmed email) keeps the full record. Tests `tests/receipt-close.test.ts`.
- Undecided audio: 90 days. "Not for me": 30 days. Kept: until the receiver deletes. Artwork and stems go with their track (the sender's receipt keeps only the stem names, `tracks.stems_sent`, so it doesn't change when the track goes); an EP/album cover passes to the folder's next remaining track instead (`handOverFolderCovers`), and goes when the last of them goes.
- Deleting an account removes every file and row it owns; files are queued in `storage_deletions` and retried until gone (with their copies in the recovery bucket; a discarded upload is deleted again once its 15-minute upload link has expired, in case it was put back); backups are kept 14 days (the privacy page promises within 30), encrypted, and hold no sessions, codes or IP addresses.
- Privacy requests (copy, erase) run from ops (super admin). Erasing a sender removes their sender records and tracks (files and stems), messages, waitlist and newsletter entries, reopen requests and every email to them (queued or sent); only the unsubscribe list (`email_suppressions`) keeps the address, so they're never emailed again. The data copy shows the same, newsletter entry included.
- Staff verification proposals and their proof files: kept while the account exists (so other teams can check why it has, or had, the mark); deleted with the account. A proof uploaded but never sent with a proposal is removed by the nightly check a week on (`file_reservations`, kind `verification_proof`).
- Deleting a collection deletes its artwork from storage (its tracks stay, unsorted); deleting an account deletes every collection's artwork too (both from 28 Oct, Batch C).
